**The two migrations are applied to production**, ahead of the code, which is
the correct order and the only safe one. This round does count rows in new
tables — the sidebar badge counts open `JobIssue` rows, and phone masking
cannot allocate a number without `ProxyNumber` — and the cleaner's job detail
page reads `JobIssue` with no error boundary. Shipping the code first would
have 500'd every cleaner's job page. Migrating first is inert: nothing
currently deployed names these tables.

```
npx prisma migrate deploy     # done, 10 Sept
git push origin main          # still to do
```

What was applied, and what was checked before and after:

- Pre-flight confirmed none of the three tables already existed. That mattered:
  every `CREATE TABLE` is `IF NOT EXISTS`, so a pre-existing table of a
  different shape would have been skipped silently while Prisma still marked
  the migration applied.
- The hand-written SQL was diffed against `schema.prisma` column by column —
  types, nullability, defaults, index names, FK cascades. No drift. This was
  the real risk: these files were written by hand, not generated by
  `prisma migrate dev`, and drift would leave production with a migration
  marked applied and a client issuing queries against columns that do not
  exist.
- After: `JobIssue` 17 columns / 1 FK / 5 indexes, `ProxyNumber` 7 / 0 / 4,
  `MaskedContact` 11 / 2 / 6. All three have forced RLS, a tenant-isolation
  policy, the not-blank check and the `awer_app` grant. RLS coverage went
  103 → 106 with nothing unprotected.
- One index was added before applying, while the file was still unapplied:
  `JobIssue_organizationId_createdAt_idx`. The admin queue's default view
  filters on nothing but the workspace and orders by `createdAt`, which the
  `(organizationId, status, createdAt)` index cannot serve because `status`
  sits between the two columns it needs.

**Staging was not migrated.** `.env` holds one database URL and it is
production; there is no staging connection string here to use. If staging is
still a live environment, it needs the same `migrate deploy` before it will run
this code.

### Detail

**#1 Notifications.** The diagnosis in the fix doc was wrong in a useful way.
Every trigger was already firing: claimed, clocked in, checklist, new available
jobs. The real problems were different:

- `admin.clock.clocked_out` was set to `EMAIL: false` in the catalog. The email
  had existed and been wired since the clock shipped. One flag stopped it.
- Photo uploads had no notification at all. Added, firing on the first photo
  only, because photos upload one at a time and a mail each is eight for one
  bathroom.
- There was no in-app record of any event, only email, so sidebar badges could
  not work at all. There is now a notification centre. The event is recorded
  whether or not the email was enabled or delivered, so "we never heard about
  it" is something you check rather than guess at.

The last piece, **"admin notified when a cleaner reports an issue,"** was not a
notification fix — there was no issue-reporting feature to notify about. It is
now built, and its shape was a decision, so here is the decision:

- **What a cleaner can report:** can't get in, supplies or equipment, property
  damage, job bigger than booked, safety, problem with the client, something
  else. Seven categories, each with a line of plain hint text on the picker.
- **Urgency:** two levels. "Can wait" and "I'm blocked right now."
- **Attachment:** one optional photo, compressed on the phone before upload,
  filed through the existing job-photo path as `kind: ISSUE`. An issue photo is
  deliberately exempt from the after-photo consent gate — that policy is about
  proof of work, not about damage a cleaner is trying to report — and it does
  not trigger the "photos added" email, because the issue's own notification
  says more.
- **What happens next:** the admin sees it three ways — a sidebar badge counting
  open issues, a new `/admin/issues` page with Open / Acknowledged / Resolved
  filters, and a card on the job itself. Acknowledge, then resolve with an
  optional note. The cleaner sees their own reports and the resolution note on
  the job page.
- **Why the categories are a TypeScript union and not a Prisma enum:** widening
  an enum costs a migration. The next category should cost one line.

The in-app record is written before and outside every toggle, following the rule
the notification centre already set: the toggles decide what is *sent*, not what
*happened*.

**#3 Hamburger.** Unchanged, and still the one item nobody has actually looked
at. `Sidebar.tsx` renders `md:hidden fixed top-4 left-4 z-30` with a backdrop, a
drawer and a close button, and the layout reserves `pt-16` for it. It has been
there since 25 June. The Sept 3 screenshot shows it missing, so either that was
a stale build or something on the dashboard covers it. **Load `/admin` on a
phone before we spend time here.**

**#4 Required cleaner count.** The column was read everywhere already: spots
open in the cleaner app, the claim cap, "N of M assigned" on the calendar,
partial staffing on web bookings. There is now a field on the job form with the
shortfall said out loud while the admin is still on the crew picker.

The warning before starting or completing is now built too. Three decisions
inside it worth recording:

- **It warns, it never blocks.** No disabled buttons and no server refusal. The
  codebase already states this policy for assignment warnings — *"an admin
  knowingly booking a cleaner outside their hours is an allowed decision"* — and
  the same logic is stronger here: refusing to let a cleaner clock in because
  someone else no-showed punishes the wrong person.
- **Crew size is the count of distinct people**, the union of the job's lead and
  its roster. A claimer is written into both, so adding them double-counts; an
  admin-assigned lead can sit outside the roster, so ignoring them undercounts.
  The union errs toward warning less, which is right for an advisory.
- **A short-handed completion is recorded.** When the final clock-out finishes
  an under-staffed job, a `JobLog` row lands beside the status change. "Was that
  job done short?" should be a lookup, not a memory.

**#6 Client phone.** Was already half-right: the phone is excluded from
available job previews, and `provider.showCustomerPhone` gates it even for
assigned cleaners. But every cleaner who had ever been assigned a job kept that
customer's mobile number permanently, and no setting could undo that.

Masking is now built. How it works:

- A workspace buys Twilio numbers and adds them to a pool
  (Settings → Connectors → Masked numbers). The receptionist number is left
  alone — it is `@unique` and singular by design, because it is how an inbound
  text is routed back to the right workspace.
- When a cleaner opens a job, one pool number is paired to that
  (cleaner, customer) couple. They see the pool number, not the customer's, with
  both a call and a text link. The customer's real number is never sent to the
  browser at all in this state — not in the markup, not in a title attribute,
  not in any client component's props.
- Texts to a pool number are relayed to the other party, prefixed with who is
  speaking. Calls are bridged with `<Dial>`, with the pool number as caller ID.
  Neither leg ever reaches the AI receptionist or job chat.
- A pairing expires 24 hours after the job ends, and expired pairings are swept
  on allocation and by the daily cron, so the pool does not silently exhaust.
- Off by default. `provider.maskCustomerPhone` starts `false`, because it does
  nothing useful until a workspace owns pool numbers, and a setting's default
  must equal today's behaviour.
- When it cannot mask — masking off, no numbers, no phone on one side — it falls
  back to exactly the old behaviour. The one loud case is an exhausted pool,
  which tells the cleaner to call the office, because that is a real failure
  somebody has to go and fix.

**This has never spoken to Twilio.** It compiles, its pure logic is covered by
69 checks, and no call or text has been placed through it. See section 5.

**#10 Per-cleaner pay.** Unchanged: fully working for a fixed dollar amount per
cleaner, with a guarantee the crew can never be paid more than the agreed total.
Percentage and hourly remain job-level. The per-person `$ / % / hr` selector in
the BookingKoala screenshot changes payroll maths and still needs a decision —
it is the only thing left in section 6 that is ours to build.

**#11 Preview panel.** Done. It already carried contact rows, address, booking
ID, postal code, service, frequency, property, assignment, payment method,
prices, pay model, description and notes. What each cleaner is being paid is now
there too, and — more usefully — it is the *same* number the Financials tab
shows. It was not before: the drawer printed the base share and the job page
printed the total, so tips and transportation made the two disagree by a few
dollars with nothing on screen to explain it.

**Pool sizing is not a free choice.** One pool number can carry exactly one
(cleaner, customer) pairing at a time — an inbound text gives us only the number
dialled and the number it came from, so two pairings sharing a number would make
"who did they mean?" unanswerable. Pairings live from the moment a cleaner opens
the job until a day after it ends. Size the pool against overlapping jobs, not
against total jobs.

### Never tested against a real service

**Subscriptions have never run against a live Stripe account.** Signup, trial,
card, plan switch, failed payment and cancel are all written and typecheck, and
the money arithmetic is covered by tests, but no real card has ever gone
through this code. That is the single biggest untested risk before Oct 1.

**Phone masking has never run against Twilio**, and joins that list today. The
routing logic, the TwiML, the signature order and the escaping are covered by
tests; no call has been bridged and no text relayed. It is second on the list
only because it fails visibly and locally, where a bad subscription fails
quietly and takes money with it.
